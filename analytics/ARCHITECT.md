## 1. Problem Statement

**EN summary.** When code in `Orya*` repositories is generated by an AI agent via `opencode`, the human author loses the mental map of decisions and rejected alternatives. `OryaCodeAuthorityFirst` restores authorship by recording provenance, archiving decisions, and applying spaced repetition to the author's own knowledge of the codebase.

Когда код в репозиториях `Orya*` пишется не человеком, а AI-агентом через `opencode`, возникает специфическое отчуждение. Файл `auth/policy.go` в `OryaSecurity` существует, компилируется, проходит тесты — но в голове автора нет истории его появления. Не зафиксированы рассмотренные альтернативы (RBAC vs ABAC, policy-as-code vs embedded rules), не сохранены тупиковые ветки, которые агент попробовал и откатил, не сохранено обоснование выбора `dieseldb` как storage layer вместо SQLite. Git log показывает «refactor auth middleware» — но это память агента, а не память человека.

Это критично, потому что владение кодом — это не знание синтаксиса, а **ментальная карта принятых решений и отвергнутых альтернатив**. Без неё невозможно безопасно эволюционировать систему: каждое следующее изменение принимается в вакууме, риск регрессий растёт, а обсуждение архитектуры с контрибьюторами превращается в «спрошу у агента».

`OryaCodeAuthorityFirst` — инструмент, который восстанавливает ощущение авторства. Он не пишет код за автора и не заменяет `opencode`. Он делает так, чтобы через неделю, месяц или год после AI-сессии автор мог открыть любой файл в любом из пяти репо `Orya*` и сказать: «Я понимаю, почему здесь именно так, и могу объяснить это другому разработчику».

## 2. Design Principles

**EN summary.** Six principles govern all architectural decisions below: Authorship-first, Provenance by default, Decision > Implementation, Spaced repetition of code, First-person voice, Cross-repo mental graph. Any feature failing to advance the primary metric (Authorship Confidence Score) is excluded from v0.1.

Инструмент строится на шести принципах, которые определяют все архитектурные решения ниже.

**Authorship-first.** Главная метрика — не покрытие кода тестами и не скорость разработки, а субъективная уверенность автора: «я могу объяснить этот код так, как будто написал его сам». Любая фича оценивается через этот критерий; фичи, не двигающие Authorship Confidence Score (см. секцию 12.1), не попадают в v0.1.

**Provenance by default.** Происхождение каждого нетривиального коммита (какой промпт, какая сессия, какая итерация) записывается автоматически, без участия человека. Хранение provenance — это базовый слой, на котором строятся остальные модули; отсутствие provenance делает два других модуля бесполезными, поскольку им не к чему привязывать записи.

**Decision > Implementation.** Понимание «как» вторично по отношению к пониманию «почему». Инструмент тратит больше ресурсов на фиксацию отвергнутых альтернатив, чем на объяснение финальной реализации — финальную реализацию можно прочитать в коде, альтернативы же исчезают без следа и через полгода становятся недоступными для реконструкции.

**Spaced repetition of code.** Ментальная карта затухает без подкрепления — эмпирически этот порог составляет 4-6 недель. Применяется алгоритм SM-2 (как в Anki) к ключевым файлам и решениям, чтобы через 30/60/90 дней после коммита они автоматически возвращались в зону внимания автора без ручного управления расписанием.

**First-person voice.** Все генерируемые объяснения пишутся от лица автора: «Я выбрал RBAC вместо ABAC, потому что на тот момент у нас было всего три роли и накладные расходы ABAC не оправдывались». Это не стилистический выбор, а когнитивный трюк — первое лицо заставляет ассимилировать решение как собственное, а не как внешне навязанное.

**Cross-repo mental graph.** Пять репо `Orya*` — один продукт. Инструмент хранит граф зависимостей между ними: «`OryaAgent` зависит от `OryaSecurity` через интерфейс `PolicyEvaluator`, который определён в `OryaSecurity/pkg/policy/evaluator.go:42`». При изменении интерфейса в одном репо инструмент подсказывает, какие решения в других репо могут стать неактуальными.

## 3. System Architecture

**EN summary.** Three independent layers compose the system: Interface Layer (CLI + MCP server), Storage Layer (`.orya/` folder committed to each repo's git history), Hooks Layer (pre-session / post-edit / pre-commit integrated with `opencode`). Storage in-repo guarantees checkout time-travel: a `git checkout` to an old commit reveals the mental map as it was at that moment.

`OryaCodeAuthorityFirst` состоит из трёх слоёв, каждый из которых можно использовать независимо, но вместе они дают синергетический эффект.

### 3.2 Why this composition

Хранение `.orya/` в самом репозитории (а не в отдельной БД) гарантирует, что provenance и decisions эволюционируют синхронно с кодом: `git checkout` на старый коммит даёт доступ к ментальной карте того момента. Хуковая интеграция с `opencode` минимизирует трение — автор не должен явно вызывать `orya log`, журнал сессий пишется автоматически. CLI и MCP-сервер дают два режима потребления: CLI для дневной работы в терминале, MCP — для автоматического инжектирования контекста в новые AI-сессии.

Ядро системы — три модуля: **Provenance Tracker**, **Decision Log**, **Mental Model Reconstructor**. Они описаны в следующих трёх секциях.

## 4. Module Specifications

### 4.1 Provenance Tracker

**EN summary.** Each `opencode` session receives a unique `session_id` and auto-logs to `.orya/sessions/<id>.yml` with the original prompt, iterations, files touched, final commit SHA, and references to decisions made. `git blame` is patched via a `post-commit` trailer `Orya-Session: <id>` so plain `git log --grep` finds provenance without a separate tool.

Provenance Tracker отвечает на вопрос «откуда взялся этот код». Каждая сессия `opencode` получает уникальный `session_id` и автоматически логирует себя в `.orya/sessions/<id>.yml`. Запись содержит исходный промпт, итерации, затронутые файлы, финальный коммит (если был) и ссылку на git-объект.

**Схема записи сессии:**

```yaml
# .orya/sessions/2026-10-24-a1b2c3.yml
session_id: 2026-10-24-a1b2c3
repo: OryaSecurity
started_at: 2026-10-24T11:02:14+03:00
ended_at: 2026-10-24T11:47:33+03:00
agent: opencode
model: glm-4.6
tool_call: opencode run "add rate limiter to /v1/policies"
initial_prompt: |
  Нужно добавить rate limiter на endpoint POST /v1/policies.
  Сейчас любой клиент может спамить запросами. Ограничение:
  10 запросов в минуту на токен.
iterations:
- id: i1
  action: read
  target: internal/api/policies.go
- id: i2
  action: edit
  target: internal/api/policies.go
  diff_summary: "добавлен middleware RateLimit(token, 10/min)"
- id: i3
  action: edit
  target: internal/middleware/ratelimit.go  # новый файл
files_touched:
- internal/api/policies.go
- internal/middleware/ratelimit.go
commit_sha: 9f3e2a1  # null если не закоммичено
decisions_made:
- d_2026-10-24-01  # ссылка на .orya/decisions/d_2026-10-24-01.md
voice_signature: "rate limiter нужен был срочно, выбрал token bucket"
```

**Связь с `git blame`.** Provenance Tracker патчит `git blame` через `post-commit` hook: каждый коммит, сделанный через `opencode`, помечается trailer `Orya-Session: 2026-10-24-a1b2c3`. Это позволяет обычному `git log --grep=Orya-Session` находить происхождение кода без отдельного инструмента и без обучения команды новым командам.

**CLI-команды модуля:**

```bash
# Кто написал эту строку и в какой сессии?
orya who internal/api/policies.go:42
# → session 2026-10-24-a1b2c3, prompt: "add rate limiter", iteration i2

# Когда в этом файле появился паттерн X?
orya when --pattern "token_bucket" internal/middleware/
# → 2026-10-24, session a1b2c3, commit 9f3e2a1

# Почему (вытягивает decision log для этого файла)
orya why internal/middleware/ratelimit.go
# → d_2026-10-24-01: выбран token bucket вместо sliding window
#   потому что накладные расходы на окно не оправданы при 10 req/min
```

Provenance — это базовый слой. Без него два других модуля не работают: Decision Log не к чему привязать решения, Mental Model Reconstructor не из чего генерировать карточки.

### 4.2 Decision Log

**EN summary.** ADR-like records stored in `.orya/decisions/d_<date>-<seq>.md`. Unlike canonical ADRs, the primary value is the list of **rejected alternatives** — the chosen path can be read from code, alternatives vanish without explicit capture. Triggered by `post-edit` hook after non-trivial edits (>50 LOC, excluding imports / formatting / test-duplicates) and enforced by `pre-commit` hook.

Decision Log — это архив отвергнутых альтернатив. Каждое нетривиальное решение в коде `Orya*` получает файл `.orya/decisions/<id>.md` в формате, похожем на ADR (Architecture Decision Record), но с одним принципиальным отличием: **главная ценность — не в описании выбранного варианта, а в фиксации отвергнутых**.

Финальную реализацию можно прочитать в коде. Альтернативы же без явной фиксации исчезают бесследно, и через полгода автор не помнит, почему не выбрал тот путь, который сейчас кажется очевидным.

**Схема decision-записи:**

```markdown
---
id: d_2026-10-24-01
title: Rate limiter: token bucket vs sliding window
date: 2026-10-24
repo: OryaSecurity
session: 2026-10-24-a1b2c3
files:
- internal/middleware/ratelimit.go
status: accepted
---

## Контекст
POST /v1/policies принимает запросы создания политик. Без ограничения
любой валидный токен может выполнить DoS, забив очередь обработки.
Нужно ограничение 10 запросов в минуту на токен.

## Выбрано
Token bucket: 10 токенов в бакете, пополнение 1 токен/6 секунд.

## Альтернативы

### Sliding window
- Что: считать запросы в скользящем окне 60 секунд
- Почему отверг: при 10 req/min накладные расходы на хранение
  временных меток не оправданы. Sliding window имеет смысл
  при 100+ req/sec, у нас на 3 порядка меньше.

### Fixed window
- Что: считать запросы в фиксированных минутных окнах
- Почему отверг: на границе окна возможен всплеск 2x (10+10),
  что для политик критично — каждая политика тяжёлая.

### Redis-based distributed limiter
- Что: вынести счётчик в Redis
- Почему отверг: на данном этапе нет требования multi-instance.
  Добавит сетевую задержку и точку отказа. Перенести в Redis
  можно позже без изменения интерфейса Limiter.

## Импликации
- Если нагрузка вырастет до 100+ req/sec — пересмотреть в сторону
  sliding window + Redis.
- Интерфейс Limiter абстрактен, миграция без боли.
- Метрики: размер бакета вынесен в конфиг, можно тюнить без релиза.
```

**Триггеры записи.** Decision log не пишется вручную — это не работало бы. Записи инициируются хуком `post-edit` в opencode: после каждой AI-сессии, изменившей >50 строк нетривиального кода, хук предлагает автору за 30 секунд заполнить шаблон через интерактивный промпт в терминале. Если автор пропускает — `pre-commit` хук напоминает ещё раз и блокирует коммит, пока не появится ссылка на decision (или явная пометка `trivial: true`).

**CLI-команды модуля:**

```bash
# Все решения за сегодня
orya decisions --today

# Решения, влияющие на конкретный файл
orya decisions --file internal/middleware/ratelimit.go

# Решения без связанных коммитов (прорехи в логе)
orya decisions --gaps

# Поиск по ключевому слову среди отвергнутых альтернатив
orya decisions --search "Redis"

# Интерактивное создание новой записи
orya decisions new --files internal/middleware/ratelimit.go
```

Decision Log — это долгосрочная память проекта. Через год автор сможет ответить на вопрос «почему у нас нет Redis-сессий» не выдумкой, а ссылкой на конкретную запись.

### 4.3 Mental Model Reconstructor (MMR)

**EN summary.** The most goal-critical module. Converts passive code-reading ability into active ownership via SM-2 spaced repetition over three card types: "Why X here?", "What if Y is removed?", "Where is Z handled?". Cards are generated automatically from `.orya/sessions/` and `.orya/decisions/`. A cross-repo dependency graph in `.orya/mental-model/graph.yml` enables cards of types 2 and 3, and surfaces "blindspots" — files changed in the last 30 days but not covered by any SRS card.

Mental Model Reconstructor (MMR) — самый важный модуль с точки зрения цели инструмента. Он превращает пассивное знание (автор может прочитать код) в активное владение (автор может объяснить код без подглядывания).

MMR применяет алгоритм интервального повторения SM-2 (тот же, что в Anki) к трём типам карточек, генерируемых из `.orya/sessions/` и `.orya/decisions/`.

**Тип 1 — «Почему здесь X?»** Карточка привязана к конкретному файлу и строке. Вопрос: «Почему в `internal/middleware/ratelimit.go:18` выбран token bucket, а не sliding window?». Ответ сверяется с `d_2026-10-24-01`. Карточка генерируется автоматически при создании decision-записи и обеспечивает прямое подкрепление связи «файл ↔ решение».

**Тип 2 — «Что будет если удалить Y?»** Карточка симулирует удаление ключевого компонента и просит предсказать эффект. Пример: «Что произойдёт, если удалить `policy.Cache` из `OryaSecurity/pkg/policy/evaluator.go`?». Правильный ответ: «Латентность eval вырастет с 2ms до 40ms, потому что каждый запрос пойдёт в `dieseldb` без in-memory кэша». Эти карточки генерируются из графа зависимостей и проверяют понимание не отдельного решения, а архитектурной связности.

**Тип 3 — «Где обрабатывается Z?»** Карточка проверяет знание потока данных. Пример: «Где в коде `OryaAgent` обрабатывается событие `tool_call_failed`?». Ответ должен включать путь от ingestion до retry-логики. Эти карточки выявляют «слепые зоны» — части системы, которые автор никогда не трогал, но которые влияют на его код через события и интерфейсы.

**Алгоритм SM-2.** Каждая карточка имеет поле `ease_factor` (начально 2.5) и `interval` (начально 1 день). После ответа автор оценивает качество от 0 до 5. Оценка <3 сбрасывает интервал до 1 дня. Оценка ≥4 увеличивает интервал на `ease_factor`. Карточки с оценкой 3 остаются на прежнем интервале. Это стандартный SM-2 без модификаций.

**Формат хранения:**

```yaml
# .orya/mental-model/cards.yml
cards:
- id: c_001
  type: why
  repo: OryaSecurity
  file: internal/middleware/ratelimit.go
  line: 18
  question: "Почему выбран token bucket?"
  expected_answer: "10 req/min, накладные расходы sliding window не оправданы"
  decision_ref: d_2026-10-24-01
  ease: 2.5
  interval_days: 1
  due: 2026-10-25
  last_reviewed: null
  reviews: []
- id: c_002
  type: what_if_remove
  repo: OryaSecurity
  target: policy.Cache
  file: pkg/policy/evaluator.go
  question: "Что произойдёт если удалить policy.Cache?"
  expected_answer: "латентность eval 2ms → 40ms, каждый запрос в dieseldb"
  ease: 2.3
  interval_days: 6
  due: 2026-10-30
```

**Граф зависимостей.** MMR строит и поддерживает кросс-репо граф: импорты, вызовы интерфейсов, события. Граф хранится в `.orya/mental-model/graph.yml` и обновляется при каждом `orya sync`. Граф нужен для генерации карточек типов 2 и 3, а также для подсветки «слепых зон» — файлов, которые изменились за последние 30 дней, но не попали ни в одну SRS-карточку.

**CLI-команды модуля:**

```bash
# Ежедневная сессия повторения (10 минут, ~15 карточек)
orya review
# → показывает карточки, чьи due ≤ сегодня

# Жёсткая сессия: только карточки с низким ease
orya review --hard

# Просмотр слепых зон
orya review --blindspots
# → 23 файла в OryaAgent изменены за 30 дней, но не в SRS

# Принудительно сгенерировать карточки из последних решений
orya review --regenerate --since 7d

# Статистика владения
orya review --stats
# → Recall rate: 78%, coverage: 64% файлов, blindspots: 23
```

MMR — это механика, которая превращает «AI написал, я одобрил» в «я владею этим кодом». Без интервального повторения ментальная карта тает за 4-6 недель.

## 5. Data Model — `.orya/` Contracts

**EN summary.** `.orya/` lives at the root of every `Orya*` repo and is committed alongside code. Five subdirectories + three top-level files. All schemas are YAML/Markdown to maximize diffability and avoid binary blobs in git history.

Папка `.orya/` живёт в корне каждого репозитория `Orya*` и коммитится вместе с кодом. Это гарантирует синхронизацию ментальной карты с состоянием репо на любом коммите.

### 5.1 File tree

```text
.orya/
├── context.md              # автоматически генерируемый контекст для pre-session hook
├── manifest.yml            # мета-информация о репо и связях с другими репо Orya*
├── sessions/               # Provenance Tracker
│   ├── 2026-10-24-a1b2c3.yml
│   └── 2026-10-25-d4e5f6.yml
├── decisions/              # Decision Log
│   ├── d_2026-10-24-01.md
│   ├── d_2026-10-24-02.md
│   └── index.yml           # быстрый индекс для поиска
├── mental-model/           # Mental Model Reconstructor
│   ├── cards.yml           # SRS-карточки
│   └── graph.yml           # кросс-репо граф зависимостей
└── reviews/                # история orya review сессий
    └── 2026-10-24.log
```

### 5.2 `manifest.yml`

Связующий файл между репо. Пример для `OryaAgent`:

```yaml
# .orya/manifest.yml в репозитории OryaAgent
repo: OryaAgent
role: orchestrator  # orchestrator | security | observability | ai | hs
description: |
  Оркестратор Orya-стека. Запускает агентов, маршрутизирует события,
  хранит conversation state.
depends_on:
- repo: OryaSecurity
  interface: github.com/Reider85/OryaSecurity/pkg/policy.Evaluator
  used_in: internal/orchestrator/policy.go:42
  decision: d_2026-09-15-03  # почему именно этот интерфейс
- repo: OryaObservability
  interface: github.com/Reider85/OryaObservability/pkg/tracer
  used_in: internal/orchestrator/tracing.go:18
- repo: dieseldb  # внешняя зависимость
  interface: github.com/Reider85/dieseldb.Client
  used_in: internal/storage/diesel.go
exposes:
- interface: AgentRunner
  package: github.com/Reider85/OryaAgent/pkg/runner
  consumers: [OriaAI, OriaHS]
principles:
- "Оркестратор не содержит бизнес-логики, только маршрутизацию"
- "Все долгоживящие состояния — в dieseldb, не в памяти"
- "Каждая ошибка агента логируется в OryaObservability с trace_id"
```

`depends_on[].decision` — обратная ссылка на `.orya/decisions/`, объясняющая выбор интерфейса. При `orya sync` инструмент проверяет, что все referenced decisions существуют, и warns при их отсутствии.

### 5.3 `context.md`

Генерируется командой `orya context` и перегенерируется автоматически при каждом коммите. Содержит выжимку для AI-агента: принципы, последние 10 decisions, активные слепые зоны, интерфейсы, которые репо экспортирует/потребляет. **Длина — строго до 2000 токенов**, чтобы помещаться в system prompt без переполнения контекста.

Алгоритм генерации:

1. Прочитать `manifest.yml` → секция `principles` + `exposes` + `depends_on`.
2. Прочитать `decisions/index.yml`, взять последние 10 по полю `date`.
3. Прочитать `mental-model/graph.yml`, вычислить blindspots (файлы, изменённые за 30 дней, не покрытые карточками).
4. Скомпоновать markdown ≤2000 токенов; при превышении приоритезация: `principles > blindspots > decisions > exposes`.

### 5.4 `sessions/*.yml`

См. секцию 4.1. Именование: `<YYYY-MM-DD>-<short_id>.yml`, где `short_id` — первые 6 hex-символов SHA-256 от `started_at + initial_prompt`. Гарантирует глобальную уникальность в пределах репо и стабильность при повторных генерациях.

### 5.5 `decisions/*.md` и `decisions/index.yml`

См. секцию 4.2 для формата отдельной записи. `index.yml` — индекс для быстрого поиска по тегам, файлам, репо:

```yaml
# .orya/decisions/index.yml
- id: d_2026-10-24-01
  title: Rate limiter: token bucket vs sliding window
  date: 2026-10-24
  repo: OryaSecurity
  files:
  - internal/middleware/ratelimit.go
  tags: [rate-limiting, middleware, token-bucket]
  status: accepted
- id: d_2026-10-24-02
  title: ...
```

Без `index.yml` `orya decisions --search` парсил бы все markdown-файлы при каждом вызове. Индекс обновляется хуком `post-edit` после создания/изменения любой decision-записи.

### 5.6 `mental-model/cards.yml` и `graph.yml`

См. секцию 4.3 для формата карточек. `graph.yml` — кросс-репо граф зависимостей в YAML-формате:

```yaml
# .orya/mental-model/graph.yml
nodes:
- repo: OryaSecurity
  file: pkg/policy/evaluator.go
  symbol: Cache
  kind: struct
- repo: OryaAgent
  file: internal/orchestrator/policy.go
  symbol: evaluator
  kind: usage
edges:
- from: {repo: OryaAgent, file: internal/orchestrator/policy.go, line: 42}
  to:   {repo: OryaSecurity, file: pkg/policy/evaluator.go, symbol: Evaluator}
  kind: import
  decision: d_2026-09-15-03
last_synced: 2026-10-24T11:00:00+03:00
```

Граф строится из `go list -json ./...` + статического анализа вызовов интерфейсов. Обновляется `orya sync`, который автор запускает после `git pull` или при добавлении новой зависимости.

## 6. Hooks Contracts

**EN summary.** Three opencode hook points: `pre-session` (injects `context.md` into agent's system prompt), `post-edit` (writes provenance draft after each iteration; for >50 LOC non-trivial edits, prompts author for a decision record), `pre-commit` (blocks commits lacking `Orya-Session` trailer or decision reference, unless `Orya-Trivial: true`). All hooks fail-safe: if `orya` binary is unavailable, `opencode` continues with a warning, sessions are never blocked.

Интеграция с `opencode` — это хуковой слой, который делает `OryaCodeAuthorityFirst` невидимым в дневной работе. Автор не вызывает `orya log` вручную — журнал сессий пишется автоматически через три типа хуков.

### 6.1 Pre-session hook

**Trigger:** `opencode run` start.
**Input:** `$ORYA_REPO` (путь к корню репо), `$ORYA_SESSION` (новый `session_id`).
**Action:**

1. Читать `.orya/context.md`.
2. Если файл отсутствует или старше последнего коммита — запустить `orya context --refresh`.
3. Инжектировать содержимое в system prompt агента.

**Effect:** Агент с первой итерации знает, что в `OryaSecurity` выбран token bucket, и не предложит sliding window заново. Это сокращает количество итераций и устраняет класс регрессий вида «агент переписал существующее решение, потому что не знал о нём».

### 6.2 Post-edit hook

**Trigger:** после каждой итерации `opencode`, изменившей файлы.
**Input:** `$ORYA_REPO`, `$ORYA_SESSION`, дифф изменённых файлов.
**Action:**

1. Автоматически создать/обновить `.orya/sessions/<session_id>.yml` с затронутыми файлами и diff-сводкой.
2. Подсчитать «нетривиальные» изменения: >50 строк, исключая imports, форматирование, тесты-дубликаты.
3. Если порог пройден — прервать сессию и предложить автору за 30 секунд заполнить decision-шаблон через TUI-промпт.
4. Автор может пропустить с пометкой `trivial: true`; в этом случае `pre-commit` спросит ещё раз.

### 6.3 Pre-commit hook

**Trigger:** перед `git commit`.
**Input:** staged diff.
**Action:**

1. Проверить наличие trailer `Orya-Session: <id>` в message коммита (его ставит `post-edit`).
2. Если коммит нетривиален (>50 строк, не только тесты/документация) и не ссылается ни на один decision — **заблокировать коммит**.
3. Вывести подсказку: «У этого изменения нет записи в Decision Log. Создать? (y/n/t — trivial)».
4. При `y` — запустить `orya decisions new` интерактивно.
5. При `t` — добавить trailer `Orya-Trivial: true` и разрешить коммит.
6. При `n` — отказ от коммита.

Это сознательное трение: оно заставляет фиксировать решение до того, как код уйдёт в историю.

### 6.4 Configuration

Хранится в `~/.config/opencode/hooks.toml` и активируется командой `orya init`:

```toml
# ~/.config/opencode/hooks.toml
[[hooks]]
event = "pre-session"
command = "orya hook pre-session --repo $ORYA_REPO"

[[hooks]]
event = "post-edit"
command = "orya hook post-edit --repo $ORYA_REPO --session $ORYA_SESSION"

[[hooks]]
event = "pre-commit"
command = "orya hook pre-commit --repo $ORYA_REPO"
```

### 6.5 Fail-safe semantics

Хуки спроектированы так, чтобы не ломать workflow при сбое:

- Если `orya` binary недоступен → `opencode` продолжает работать, в логе warning, сессия не блокируется.
- Если `.orya/` отсутствует → hook молча пропускается (репо не инициализирован через `orya init`).
- Если `context.md` повреждён → `orya context --refresh` запускается принудительно.
- При конфликте `trivial: true` и нетривиального диффа → `pre-commit` всё равно требует decision или явного `Orya-Trivial: true` trailer.

Это важно для продуктивности — инструмент не должен становиться узким местом. Подробное обоснование см. в ADR-003 (секция 11).

## 7. Sequence Flows

**EN summary.** Three canonical flows: (1) prompt → git commit through all three modules in a daily workflow; (2) SRS card lifecycle from generation to review and ease update; (3) cross-repo change propagation when an interface in one repo is modified, surfacing potentially stale decisions in dependents.

### 7.1 Prompt → git commit (дневной поток данных)

```text
[author]            [opencode]       [hooks]            [.orya/]
   │                    │                │                  │
   │  opencode run      │                │                  │
   ├───────────────────►│ pre-session    │                  │
   │                    ├───────────────►│ read context.md  │
   │                    │                ├─────────────────►│
   │                    │                │◄─────────────────┤ markdown
   │                    │ inject to      │                  │
   │                    │ system prompt  │                  │
   │                    │                │                  │
   │  (agent works)     │                │                  │
   │                    │ iteration i1   │                  │
   │                    ├───────────────►│ post-edit        │
   │                    │                ├─────────────────►│ write sessions/
   │                    │                │                  │ <id>.yml
   │                    │ iteration i2   │                  │
   │                    ├───────────────►│ post-edit        │
   │                    │                │ >50 LOC? → TUI   │
   │                    │                │ prompt author    │
   │  (fill decision)   │                │                  │
   │◄───────────────────┤                │                  │
   │                    │                ├─────────────────►│ write decisions/
   │                    │                │                  │ d_*.md
   │  git commit        │                │                  │
   ├───────────────────►│                │ pre-commit       │
   │                    ├───────────────►│ validate         │
   │                    │                │ trailer +         │
   │                    │                │ decision ref     │
   │                    │                │ pass             │
   │  commit created    │                │                  │
   │◄───────────────────┤                │ post-commit      │
   │                    │                ├─────────────────►│ add trailer
   │                    │                │                  │ Orya-Session
```

### 7.2 SRS card lifecycle

## 8. MCP Interface

**EN summary.** MCP server `orya-mcp` exposes 5 tools and 3 prompts to any MCP-compatible client (opencode, Cursor, Claude Code, Cline). The flagship tool `orya.first_person_explain` returns a first-person narrative explaining a file's history, decisions, and rejected alternatives — this is the canonical way to "re-experience" authorship of a file you have not touched in months.

MCP-сервер `orya-mcp` выставляет инструменты и промпты, которые может вызывать любой MCP-совместимый клиент: `opencode`, Cursor, Claude Code, Cline. Это второй способ потребления (первый — CLI).

### 8.1 MCP-tools

| Tool | Описание | Возвращает |
|---|---|---|
| `orya.context` | Текущий контекст репо (то же, что `context.md`) | Markdown, ~2000 токенов |
| `orya.provenance` | История сессий, затронувших файл/строку | Список сессий с промптами |
| `orya.decisions` | Поиск decisions по тегам/файлам/репо | Список decision summary |
| `orya.mental_model` | SRS-карточки для текущего пользователя | JSON с due-карточками |
| `orya.first_person_explain` | **Главное:** объясняет файл от первого лица | Markdown-нарратив |

### 8.2 `orya.first_person_explain` — flagship tool

Принимает путь к файлу и возвращает объяснение, написанное от лица автора:

```text
Tool: orya.first_person_explain
Input: { "file": "internal/middleware/ratelimit.go", "depth": "medium" }

Output (markdown):

## internal/middleware/ratelimit.go

Я добавил этот файл 24 октября, в сессии про rate limiting на
POST /v1/policies (session 2026-10-24-a1b2c3). На тот момент у
нас был открытый endpoint без ограничений, и любой валидный
токен мог заDoSить очередь обработки.

Я выбрал token bucket на 10 токенов с пополнением 1/6 сек.
Смотрел sliding window, но при 10 req/min накладные расходы
на хранение меток не оправданы — sliding window имеет смысл
при 100+ req/sec, у нас на три порядка меньше. Redis-based
вариант отверг, потому что multi-instance пока не нужен,
а точка отказа не нужна. Интерфейс Limiter абстрактен,
перенести в Redis можно без боли.

Что важно помнить: размер бакета вынесен в конфиг, можно
тюнить без релиза. Метрики экспортируются в OryaObservability
как ratelimit_deny_total — если она растёт, значит лимит
слишком агрессивный.
```

Глубина `depth` принимает значения `short` (1 параграф, только решение), `medium` (решение + главные альтернативы), `long` (полная археология: все итерации сессии, все отвергнутые альтернативы, метрики). Narратив генерируется LLM (z-ai-web-dev-sdk или локальная модель), но фактические данные — `session_id`, `decisions_made`, `expected_answer` карточек — берутся строго из `.orya/`, что устраняет риск галлюцинаций на фактологической части.

### 8.3 MCP-prompts

Готовые шаблоны для типичных задач:

- `orya.pre_session_brief` — что показать агенту перед началом работы. Включает `context.md` + список активных blindspots + последние 3 decisions по теме предстоящей задачи.
- `orya.code_review_with_provenance` — ревью коммита с учётом исходного промпта и отвергнутых альтернатив. Сравнивает «что просили» vs «что сделано» vs «какие альтернативы отвергнуты».
- `orya.archaeology` — раскопки конкретного файла: когда, почему, какие альтернативы. Глубокий вариант `first_person_explain`, включающий timeline всех изменений с сессиями.

## 9. CLI Reference

```bash
# === Инициализация ===
orya init                          # создать .orya/ в текущем репо
orya init --stack                  # инициализировать все 5 репо Orya* сразу

# === Provenance ===
orya who <file:line>               # кто и в какой сессии написал строку
orya when --pattern <regex> <dir>  # когда появился паттерн
orya why <file>                    # связать файл с decision log
orya sessions --since 7d           # список сессий за период
orya sessions --gaps               # коммиты без session trailer

# === Decision Log ===
orya decisions                     # все решения (по умолчанию за 30 дней)
orya decisions --today             # только сегодняшние
orya decisions --file <path>       # влияющие на файл
orya decisions --search <query>    # полнотекстовый поиск по текстам
orya decisions --gaps              # нетривиальные коммиты без decision
orya decisions new [--files ...]   # интерактивное создание записи

# === Mental Model ===
orya review                        # ежедневная SRS-сессия (~10 мин)
orya review --hard                 # только карточки с низким ease
orya review --blindspots           # файлы без SRS-карточек
orya review --regenerate --since 7d
orya review --stats                # статистика владения

# === Контекст и синхронизация ===
orya context                       # вывести context.md в stdout
orya context --refresh             # перегенерировать context.md
orya sync                          # обновить кросс-репо граф
orya tour <file>                   # guided-экскурсия по файлу

# === Hook-интерфейс (вызывается opencode) ===
orya hook pre-session --repo <path>
orya hook post-edit --repo <path> --session <id>
orya hook pre-commit --repo <path>

# === Отчёты ===
orya report --day                  # дневной отчёт: что сделано, что упущено
orya report --week                 # недельная ретроспектива
orya report --ownership            # heatmap владения по файлам
```

Все команды принимают `--repo <path>` для кросс-репо операций. По умолчанию репо определяется по текущему каталогу.

### 10.3 Sync algorithm

`orya sync` работает в три шага:

1. **Local scan.** Для текущего репо запускает `go list -json ./...`, парсит импорты, ищет ссылки на `github.com/Reider85/*`.
2. **Manifest reconciliation.** Для каждого найденного `Orya*` импорта читает соответствующий `<repo>/.orya/manifest.yml` (если репо клонирован локально) или pullит через `git ls-remote` + raw GitHub.
3. **Graph update.** Записывает узлы и рёбра в `.orya/mental-model/graph.yml`, помечает stale decisions (те, где referenced interface изменился со времени последнего sync).

При обнаружении, что интерфейс в `depends_on` изменился, sync создаёт карточку типа `review-because-interface-changed` в `cards.yml`, которая появится в следующем `orya review`. Это замыкает цикл: изменение в одном репо автоматически триггерит SRS-обзор в зависимых репо.

## 11. Trade-offs / ADRs

**EN summary.** Six architectural decisions documented as ADRs below. Each ADR captures the choice, rejected alternatives, and the trigger that would cause reconsideration. ADRs follow the same format as Decision Log entries but cover system-wide choices rather than code-level ones.

### ADR-001: Storage location — in-repo `.orya/` vs separate database

**Context.** Provenance, decisions, and SRS cards need persistent storage. Options: (a) YAML/Markdown files in `.orya/` committed to git, (b) SQLite database per repo (git-ignored), (c) centralized Postgres for all `Orya*` repos.

**Chosen.** (a) In-repo `.orya/` folder, committed.

**Rejected alternatives.**

- **SQLite per repo.** Gives query performance, but breaks the "checkout time travel" property — `git checkout` to an old commit would not restore the mental map state at that commit. Requires separate backup strategy and complicates cross-repo queries.
- **Centralized Postgres.** Allows cross-repo queries natively, but introduces a SPOF and forces auth/network model. Excludes offline work and contradicts the "Provenance by default" principle (any barrier between code and provenance reduces capture rate).

**Trigger to reconsider.** If `.orya/` exceeds 50 MB in a single repo (unlikely for textual data, but possible for high-churn repos), evaluate hybrid: text files for current state, archived snapshots in compressed bundles committed as `git-lfs` assets.

### ADR-002: SRS algorithm — SM-2 vs FSRS vs Leitner

**Context.** Mental Model Reconstructor needs a spaced-repetition algorithm.

**Chosen.** SM-2 (the algorithm used by Anki since 1987).

**Rejected alternatives.**

- **FSRS (Free Spaced Repetition Scheduler).** More accurate, modern (2023+), but requires more parameters and a learning curve for the user to grade retention. Overkill for code ownership use case where the goal is "is the author still confident", not "what is the optimal review schedule".
- **Leitner system.** Simpler, but coarser intervals; does not adapt to per-card difficulty and tends to over-review easy cards.

**Trigger to reconsider.** If recall rate consistently <60% across the fleet after 90 days of usage, evaluate FSRS — it might better model difficulty of "abstract reasoning" cards (type 2) vs "fact recall" cards (type 1).

### ADR-003: Hooks vs explicit CLI calls

**Context.** Provenance and decisions could be recorded via hooks (automatic) or via explicit `orya log` commands (manual).

**Chosen.** Hooks.

**Rejected alternatives.**

- **Explicit CLI.** Author calls `orya log --session <id>` after each opencode session. Most flexible, but fails the "Provenance by default" principle — humans skip manual steps under time pressure, and capture rate collapses to <30% within 2 weeks of real use.

**Trade-off.** Hooks are slightly fragile (require opencode to support hook events `pre-session` / `post-edit` / `pre-commit`). Mitigation: fail-safe behavior (см. секцию 6.5) — if `orya` binary is unavailable, `opencode` continues with a warning.

**Trigger to reconsider.** If opencode removes hook support, fall back to a daemon polling git history with a 30-second interval. Less real-time, but preserves the "Provenance by default" property.

### ADR-004: Triviality threshold — 50 LOC

**Context.** `post-edit` and `pre-commit` hooks need a threshold above which an edit is considered "non-trivial" and requires a decision record.

**Chosen.** 50 lines, excluding imports, formatting, and test-duplicates.

**Rejected alternatives.**

- **30 lines.** Too aggressive; would block too many legitimate refactors and increase false-positive rate beyond 40%.
- **100 lines.** Too permissive; many architectural decisions happen in 50-90 line changes (e.g., adding a new middleware, replacing an interface implementation).
- **Per-file AST complexity delta.** Theoretically correct, but expensive to compute and brittle across languages — Go and Python have different AST models, and any future language support would require new heuristics.

**Trigger to reconsider.** If decision coverage consistently <70% with 50-line threshold, lower to 30. If false-positive rate >40% (authors frequently mark `trivial: true` on substantive changes), raise to 75.

### ADR-005: Schema format — YAML/Markdown vs JSON vs protobuf

**Context.** `.orya/` files need a serialization format.

**Chosen.** YAML for structured data (`sessions/*.yml`, `cards.yml`, `graph.yml`, `manifest.yml`); Markdown for human-readable documents (`decisions/*.md`, `context.md`).

**Rejected alternatives.**

- **JSON.** Strict schema, easy to parse, but no comments and poor diff readability for humans reviewing history.
- **Protobuf.** Compact, schema-enforced, but binary — kills `git diff`, requires compilation step, blocks ad-hoc inspection via `cat`.

**Trade-off.** YAML is whitespace-sensitive and has multiple parsers with subtle incompatibilities. Mitigation: pin to YAML 1.2 spec, use `gopkg.in/yaml.v3` everywhere, lint with `yamllint` in CI.

**Trigger to reconsider.** None — the format is correct for the use case. Only revisit if a fundamentally different access pattern (e.g., streaming queries over millions of cards) emerges, which is out of scope for v0.1.

### ADR-006: First-person voice in generated narratives

**Context.** `orya.first_person_explain` and decision records can be written in third person ("the author chose X") or first person ("I chose X").

**Chosen.** First person.

**Rejected alternatives.**

- **Third person.** More "objective" but creates psychological distance. The author reads "the author chose token bucket" as if reading about someone else, which defeats the assimilation goal.
- **Passive voice.** "Token bucket was chosen because..." Worst of both worlds — distance + zero agency.

**Rationale.** The cognitive trick of first-person voice forces assimilation: when you say "I chose X because Y", your brain accepts the decision as your own, which is the entire point of the tool. This is grounded in narrative psychology research on self-talk and identity consolidation.

**Trigger to reconsider.** If multi-user mode is added (out of scope for v0.1), first-person voice becomes ambiguous — would need per-author attribution ("As Anna, I chose...").

## 12. Success Metrics

**EN summary.** Four metrics must converge to target values within 8 weeks of usage: Authorship Confidence Score (ACS) ≥3.5, Decision Coverage ≥90%, Mental Model Reach ≥70%, Recall Rate ≥75%. Each metric has an explicit interpretation block describing what sub-3.0 / sub-60% / etc. signals mean for system tuning.

Инструмент считается работающим, если четыре метрики сходятся к целевым значениям за 8 недель использования.

### 12.1 Authorship Confidence Score (ACS)

Микро-опрос: после каждого `orya review` сессии автор отвечает на вопрос «Мог бы я написать этот код с нуля, если бы мне дали задачу?» от 1 до 5. Среднее за неделю — ACS.

**Target:** ≥3.5.

**Interpretation.** Ниже 3.0 → MMR генерирует слишком простые карточки, либо в проекте есть целые модули, которые автор не контролирует. Investigate via `orya review --blindspots` and `orya report --ownership`.

### 12.2 Decision Coverage

Доля нетривиальных коммитов (по `git log` за период) со связанной decision-записью.

**Target:** ≥90%.

**Interpretation.** Это самая лёгкая метрика — её тащит `pre-commit` хук. Ниже 90% означает, что хук обходится (через `Orya-Trivial: true` или через отключение хука). Если author регулярно помечает коммиты как trivial при реальной сложности — нужно поднять порог (см. ADR-004).

### 12.3 Mental Model Reach

Доля файлов в репо (взвешенная по LOC), которые покрыты хотя бы одной SRS-карточкой.

**Target:** ≥70%.

**Interpretation.** Ниже 70% → запустить `orya review --regenerate --since 30d` для создания карточек из недавних decisions и изменений. Также сигнал, что `orya sync` давно не запускался — без обновлённого графа генерация карточек типов 2 и 3 невозможна.

### 12.4 Recall Rate

Доля карточек в `orya review`, на которые автор ответил с оценкой ≥3.

**Target:** ≥75%.

**Interpretation.** Если recall rate по конкретному репо (например, `OriaHS`) систематически ниже 60% — это сигнал, что автор не владеет этим репо. Либо `orya tour` по слепым зонам, либо пересмотр архитектуры — возможно, репо нуждается в упрощении, потому что ни человек, ни AI не способны его удержать.

Метрики хранятся в `.orya/reviews/*.log` и агрегируются командой `orya report --metrics`.

## 13. Out of Scope (v0.1)

Сознательно вынесено за рамки текущей версии спецификации:

- **Web-дашборд.** CLI + MCP покрывают дневные задачи; визуализация графов отложена до v1.1. Текстовые ASCII-диаграммы в `orya report --ownership` достаточны для выявления hotspots.
- **Мульти-пользовательский режим.** Сейчас инструмент для одного автора; sync через `git push`/`pull` работает, но без слияния конфликтующих decisions. Multi-user требует per-author attribution в карточках и правил слияния при конфликте `ease_factor` — это нетривиальная задача SRS-теории.
- **Поддержка языков кроме Go.** Анализ импортов и графа зависимостей в v0.1 завязан на `go list`. Поддержка Python/TypeScript запланирована после стабилизации Go-стека; архитектурно это означает подключение language-specific adapters в `orya sync`.
- **Автоматическая генерация decision из LLM.** v0.1 требует ручного заполнения шаблона автором — это сознательное трение (см. ADR-003). LLM-assisted pre-fill рассматривается для v1.1 как опциональная фича с явным opt-in флагом `--ai-prefill`.
- **Real-time collaboration через CRDT.** Если несколько авторов одновременно работают в одном репо, конфликтующие `.orya/` изменения разрешаются через стандартный git merge. CRDT-семантика для `cards.yml` (где `ease_factor` мутирует часто) отложена до v2.0.
