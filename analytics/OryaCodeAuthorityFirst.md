# OryaSkill — инструмент авторского владения AI-генерируемым кодом

> **Версия спецификации:** 0.1
> **Охват:** Orya-стек (`OryaAgent`, `OryaSecurity`, `OryaObservability`, `OriaAI`, `OriaHS`) как единый продукт; `dieseldb` и `strangecoin` учитываются как внешние зависимости
> **Форм-фактор:** CLI + MCP-сервер с хуковой интеграцией в opencode
> **Голос реконструкции:** первое лицо («Я выбрал X потому что…»)

---

## 1. Постановка проблемы

Когда код в репозиториях `Orya*` пишется не вами, а AI-агентом через `opencode`, возникает специфическое отчуждение. Файл `auth/policy.go` в `OryaSecurity` существует, компилируется, проходит тесты — но в вашей голове нет истории его появления. Вы не помните, какие альтернативы рассматривались (RBAC vs ABAC, policy-as-code vs embedded rules), не помните тупиковых веток, которые агент попробовал и откатил, не помните, почему именно `dieseldb` был выбран как storage layer вместо SQLite. Git log показывает «refactor auth middleware» — но это не ваша память, это память агента.

Это критично, потому что владение кодом — это не знание синтаксиса, а **ментальная карта принятых решений и отвергнутых альтернатив**. Без неё вы не сможете безопасно эволюционировать систему: каждое следующее изменение будет приниматься в вакууме, риск регрессий растёт, а обсуждение архитектуры с другими контрибьюторами превращается в «спрошу у агента».

`OryaSkill` — инструмент, который восстанавливает ощущение авторства. Он не пишет код за вас и не заменяет `opencode`. Он делает так, чтобы через неделю, месяц или год после AI-сессии вы могли открыть любой файл в любом из пяти репо `Orya*` и сказать: «Я понимаю, почему здесь именно так, и могу объяснить это другому разработчику».

---

## 2. Принципы проектирования

Инструмент строится на шести принципах, которые определяют все архитектурные решения ниже.

**Authorship-first.** Главная метрика — не покрытие кода тестами и не скорость разработки, а субъективная уверенность автора: «я могу объяснить этот код так, как будто написал его сам». Любая фича оценивается через этот критерий.

**Provenance by default.** Происхождение каждого нетривиального коммита (какой промпт, какая сессия, какая итерация) записывается автоматически, без участия человека. Хранение provenance — это базовый слой, на котором строятся остальные модули.

**Decision > Implementation.** Понимание «как» вторично по отношению к пониманию «почему». Инструмент тратит больше ресурсов на фиксацию отвергнутых альтернатив, чем на объяснение финальной реализации — финальную реализацию можно прочитать в коде, альтернативы же исчезают без следа.

**Spaced repetition of code.** Ментальная карта затухает без подкрепления. Применяем алгоритм SM-2 (как Anki) к ключевым файлам и решениям, чтобы через 30/60/90 дней после коммита они автоматически возвращались в зону внимания.

**First-person voice.** Все генерируемые объяснения пишутся от вашего лица: «Я выбрал RBAC вместо ABAC, потому что на тот момент у нас было всего три роли и накладные расходы ABAC не оправдывались». Это не стилистический выбор — это когнитивный трюк, заставляющий вас ассимилировать решение как собственное.

**Cross-repo mental graph.** Пять репо `Orya*` — один продукт. Инструмент хранит граф зависимостей между ними: «`OryaAgent` зависит от `OryaSecurity` через интерфейс `PolicyEvaluator`, который определён в `OryaSecurity/pkg/policy/evaluator.go:42`». При изменении интерфейса в одном репо инструмент подсказывает, какие решения в других репо могут стать неактуальными.

## 3. Архитектура системы

`OryaSkill` состоит из трёх слоёв, каждый из которых можно использовать независимо, но вместе они дают синергетический эффект.

```
┌─────────────────────────────────────────────────────────────┐
│  Interface Layer                                            │
│  ┌───────────────┐   ┌───────────────┐                      │
│  │  orya CLI     │   │  MCP server   │  ← opencode, Cursor, │
│  │  (终端/IDE)    │   │  (stdio/SSE)  │    Claude Code       │
│  └──────┬────────┘   └──────┬────────┘                      │
│         │                   │                               │
└─────────┼───────────────────┼───────────────────────────────┘
          │                   │
┌─────────┼───────────────────┼───────────────────────────────┐
│  Storage Layer              │                               │
│  ┌─────────▼─────────────────▼─────────┐                    │
│  │  .orya/  (в каждом репо, в git)     │                    │
│  │  ├─ context.md         (текущая карта)│                  │
│  │  ├─ manifest.yml       (мета-репо)   │                  │
│  │  ├─ sessions/*.yml     (provenance)  │                  │
│  │  ├─ decisions/*.md     (decision log)│                  │
│  │  └─ mental-model/cards.yml (SRS)     │                  │
│  └─────────────────────────────────────┘                    │
└─────────────────────────────────────────────────────────────┘
          ▲
          │
┌─────────┼─────────────────────────────────────────────────────┐
│  Hooks Layer (интеграция с opencode)                         │
│  ┌──────────────┐  ┌──────────────┐  ┌──────────────┐        │
│  │ pre-session  │  │  post-edit   │  │ pre-commit   │        │
│  │ читает       │  │ пишет        │  │ валидирует   │        │
│  │ context.md   │  │ provenance   │  │ decisions    │        │
│  └──────────────┘  └──────────────┘  └──────────────┘        │
└─────────────────────────────────────────────────────────────┘
```

**Почему именно такая композиция.** Хранение `.orya/` в самом репозитории (а не в отдельной БД) гарантирует, что provenance и decisions эволюционируют синхронно с кодом: checkout на старый коммит даёт доступ к ментальной карте того момента. Хуковая интеграция с `opencode` минимизирует трение — вы не должны явно вызывать `orya log`, журнал сессий пишется автоматически. CLI и MCP-сервер дают два режима потребления: CLI для дневной работы в терминале, MCP — для автоматического инжектирования контекста в новые AI-сессии.

Ядро системы — три модуля: **Provenance Tracker**, **Decision Log**, **Mental Model Reconstructor**. Они описаны в следующих трёх секциях.

## 4. Модуль 1 — Provenance Tracker

Provenance Tracker отвечает на вопрос «откуда взялся этот код». Каждая сессия `opencode` получает уникальный `session_id` и автоматически логирует себя в `.orya/sessions/<session_id>.yml`. Запись содержит исходный промпт, итерации, затронутые файлы, финальный коммит (если был) и ссылку на git-объект.

**Схема записи сессии:**

```yaml
# .orya/sessions/2026-10-24-a1b2c3.yml
session_id: 2026-10-24-a1b2c3
repo: OryaSecurity
started_at: 2026-10-24T11:02:14+03:00
ended_at: 2026-10-24T11:47:33+03:00
agent: opencode
model: glm-4.6
tool_call: opencode run "add rate limiter to /v1/policies"
initial_prompt: |
  Нужно добавить rate limiter на endpoint POST /v1/policies.
  Сейчас любой клиент может спамить запросами. Ограничение:
  10 запросов в минуту на токен.
iterations:
  - id: i1
    action: read
    target: internal/api/policies.go
  - id: i2
    action: edit
    target: internal/api/policies.go
    diff_summary: "добавлен middleware RateLimit(token, 10/min)"
  - id: i3
    action: edit
    target: internal/middleware/ratelimit.go  # новый файл
files_touched:
  - internal/api/policies.go
  - internal/middleware/ratelimit.go
commit_sha: 9f3e2a1  # null если не закоммичено
decisions_made:
  - d_2026-10-24-01  # ссылка на .orya/decisions/d_2026-10-24-01.md
voice_signature: "rate limiter нужен был срочно, выбрал token bucket"
```

**Связь с git blame.** Provenance Tracker патчит `git blame` через post-commit hook: каждый коммит, сделанный через `opencode`, помечается trailer `Orya-Session: 2026-10-24-a1b2c3`. Это позволяет обычному `git log --grep=Orya-Session` находить происхождение кода без отдельного инструмента.

**CLI-команды модуля:**

```bash
# Кто написал эту строку и в какой сессии?
orya who internal/api/policies.go:42
# → session 2026-10-24-a1b2c3, prompt: "add rate limiter", iteration i2

# Когда в этом файле появился паттерн X?
orya when --pattern "token_bucket" internal/middleware/
# → 2026-10-24, session a1b2c3, commit 9f3e2a1

# Почему (вытягивает decision log для этого файла)
orya why internal/middleware/ratelimit.go
# → d_2026-10-24-01: выбран token bucket вместо sliding window
#   потому что накладные расходы на окно не оправданы при 10 req/min
```

Provenance — это базовый слой. Без него два других модуля не работают: Decision Log не к чему привязать решения, Mental Model Reconstructor не из чего генерировать карточки.

## 5. Модуль 2 — Decision Log

Decision Log — это архив отвергнутых альтернатив. Каждое нетривиальное решение в коде `Orya*` получает файл `.orya/decisions/<id>.md` в формате, похожем на ADR (Architecture Decision Record), но с одним принципиальным отличием: **главная ценность — не в описании выбранного варианта, а в фиксации отвергнутых**.

Финальную реализацию можно прочитать в коде. Альтернативы же без явной фиксации исчезают бесследно, и через полгода вы не помните, почему не выбрали тот путь, который сейчас кажется очевидным.

**Схема decision-записи:**

```markdown
---
id: d_2026-10-24-01
title: Rate limiter: token bucket vs sliding window
date: 2026-10-24
repo: OryaSecurity
session: 2026-10-24-a1b2c3
files:
  - internal/middleware/ratelimit.go
status: accepted
---

## Контекст

POST /v1/policies принимает запросы создания политик. Без ограничения
любой валидный токен может выполнить DoS, забив очередь обработки.
Нужно ограничение 10 запросов в минуту на токен.

## Выбрано

Token bucket: 10 токенов в бакете, пополнение 1 токен/6 секунд.

## Альтернативы

### Sliding window
- Что: считать запросы в скользящем окне 60 секунд
- Почему отверг: при 10 req/min накладные расходы на хранение
  временных меток не оправданы. Sliding window имеет смысл
  при 100+ req/sec, у нас на 3 порядка меньше.

### Fixed window
- Что: считать запросы в фиксированных минутных окнах
- Почему отверг: на границе окна возможен всплеск 2x (10+10),
  что для политик критично — каждая политика тяжёлая.

### Redis-based distributed limiter
- Что: вынести счётчик в Redis
- Почему отверг: на данном этапе нет требования multi-instance.
  Добавит сетевую задержку и точку отказа. Перенести в Redis
  можно позже без изменения интерфейса Limiter.

## Импликации

- Если нагрузка вырастет до 100+ req/sec — пересмотреть в сторону
  sliding window + Redis.
- Интерфейс Limiter абстрактен, миграция без боли.
- Метрики: размер бакета вынесен в конфиг, можно тюнить без релиза.
```

**Триггеры записи.** Decision log не пишется вручную — это не работало бы. Записи инициируются хуком `post-edit` в opencode: после каждой AI-сессии, изменившей >50 строк нетривиального кода, хук предлагает автору за 30 секунд заполнить шаблон через интерактивный промпт в терминале. Если автор пропускает — `pre-commit` хук напоминает ещё раз и блокирует коммит, пока не появится ссылка на decision (или явная пометка `trivial: true`).

**CLI-команды модуля:**

```bash
# Все решения за сегодня
orya decisions --today

# Решения, влияющие на конкретный файл
orya decisions --file internal/middleware/ratelimit.go

# Решения без связанных коммитов (прорехи в логе)
orya decisions --gaps

# Поиск по ключевому слову среди отвергнутых альтернатив
orya decisions --search "Redis"

# Интерактивное создание новой записи
orya decisions new --files internal/middleware/ratelimit.go
```

Decision Log — это долгосрочная память проекта. Через год вы сможете ответить на вопрос «почему у нас нет Redis-сессий» не выдумкой, а ссылкой на конкретную запись.

## 6. Модуль 3 — Mental Model Reconstructor

Mental Model Reconstructor (MMR) — самый важный модуль с точки зрения цели инструмента. Он превращает пассивное знание (вы можете прочитать код) в активное владение (вы можете объяснить код без подглядывания).

MMR применяет алгоритм интервального повторения SM-2 (тот же, что в Anki) к трём типам карточек, генерируемых из `.orya/sessions/` и `.orya/decisions/`.

**Тип 1 — «Почему здесь X?»** Карточка привязана к конкретному файлу и строке. Вопрос: «Почему в `internal/middleware/ratelimit.go:18` выбран token bucket, а не sliding window?». Ответ сверяется с `d_2026-10-24-01`. Карточка генерируется автоматически при создании decision-записи.

**Тип 2 — «Что будет если удалить Y?»** Карточка симулирует удаление ключевого компонента и просит предсказать эффект. Пример: «Что произойдёт, если удалить `policy.Cache` из `OryaSecurity/pkg/policy/evaluator.go`?». Правильный ответ: «Латентность eval вырастет с 2ms до 40ms, потому что каждый запрос пойдёт в `dieseldb` без in-memory кэша». Эти карточки генерируются из графа зависимостей (см. ниже).

**Тип 3 — «Где обрабатывается Z?»** Карточка проверяет знание потока данных. Пример: «Где в коде `OryaAgent` обрабатывается событие `tool_call_failed`?». Ответ должен включать путь от ingestion до retry-логики. Эти карточки выявляют «слепые зоны» — части системы, которые вы никогда не трогали.

**Алгоритм SM-2.** Каждая карточка имеет поле `ease_factor` (начально 2.5) и `interval` (начально 1 день). После ответа вы оцениваете качество от 0 до 5. Оценка <3 сбрасывает интервал до 1 дня. Оценка ≥4 увеличивает интервал на `ease_factor`. Карточки с оценкой 3 остаются на прежнем интервале.

**Формат хранения:**

```yaml
# .orya/mental-model/cards.yml
cards:
  - id: c_001
    type: why
    repo: OryaSecurity
    file: internal/middleware/ratelimit.go
    line: 18
    question: "Почему выбран token bucket?"
    expected_answer: "10 req/min, накладные расходы sliding window не оправданы"
    decision_ref: d_2026-10-24-01
    ease: 2.5
    interval_days: 1
    due: 2026-10-25
    last_reviewed: null
    reviews: []

  - id: c_002
    type: what_if_remove
    repo: OryaSecurity
    target: policy.Cache
    file: pkg/policy/evaluator.go
    question: "Что произойдёт если удалить policy.Cache?"
    expected_answer: "латентность eval 2ms → 40ms, каждый запрос в dieseldb"
    ease: 2.3
    interval_days: 6
    due: 2026-10-30
```

**Граф зависимостей.** MMR строит и поддерживает кросс-репо граф: импорты, вызовы интерфейсов, события. Граф хранится в `.orya/mental-model/graph.yml` и обновляется при каждом `orya sync`. Граф нужен для генерации карточек типов 2 и 3, а также для подсветки «слепых зон» — файлов, которые изменились за последние 30 дней, но не попали ни в одну SRS-карточку.

**CLI-команды модуля:**

```bash
# Ежедневная сессия повторения (10 минут, ~15 карточек)
orya review
# → показывает карточки, чьи due ≤ сегодня

# Жёсткая сессия: только карточки с низким ease
orya review --hard

# Просмотр слепых зон
orya review --blindspots
# → 23 файла в OryaAgent изменены за 30 дней, но не в SRS

# Принудительно сгенерировать карточки из последних решений
orya review --regenerate --since 7d

# Статистика владения
orya review --stats
# → Recall rate: 78%, coverage: 64% файлов, blindspots: 23
```

MMR — это и есть та механика, которая превращает «AI написал, я одобрил» в «я владею этим кодом». Без интервального повторения ментальная карта тает за 4-6 недель.

## 7. Интеграция с opencode

Интеграция с `opencode` — это хуковой слой, который делает `OryaSkill` невидимым в дневной работе. Вы не вызываете `orya log` вручную — журнал сессий пишется автоматически через три типа хуков.

**Pre-session hook.** Срабатывает при запуске `opencode run`. Хук читает `.orya/context.md` (см. секцию 8) и инжектирует его содержимое в system prompt агента. Контент включает: архитектурные принципы стека, список активных решений за последние 30 дней, список слепых зон, на которые стоит обратить внимание. Эффект: агент с первой итерации знает, что в `OryaSecurity` выбран token bucket, и не предложит sliding window заново.

**Post-edit hook.** Срабатывает после каждой итерации `opencode`, изменившей файлы. Хук автоматически создаёт черновик записи в `.orya/sessions/<id>.yml` с указанием затронутых файлов и diff-сводкой. Если изменение затрагивает >50 строк нетривиального кода (исключая imports, форматирование, тесты-дубликаты), хук прерывает сессию и предлагает автору за 30 секунд заполнить decision-шаблон через TUI-промпт. Автор может пропустить с пометкой `trivial: true`, но тогда `pre-commit` спросит ещё раз.

**Pre-commit hook.** Срабатывает перед `git commit`. Хук проверяет, что у коммита есть trailer `Orya-Session: <id>` (его ставит `post-edit`). Если коммит нетривиален (>50 строк, не только тесты/документация) и не ссылается ни на один decision — коммит блокируется с подсказкой: «У этого изменения нет записи в Decision Log. Создать? (y/n/t — trivial)». Это сознательное трение: оно заставляет фиксировать решение до того, как код уйдёт в историю.

**Конфигурация хуков** хранится в `~/.config/opencode/hooks.toml` и активируется командой `orya init`:

```toml
# ~/.config/opencode/hooks.toml
[[hooks]]
event = "pre-session"
command = "orya hook pre-session --repo $ORYA_REPO"

[[hooks]]
event = "post-edit"
command = "orya hook post-edit --repo $ORYA_REPO --session $ORYA_SESSION"

[[hooks]]
event = "pre-commit"
command = "orya hook pre-commit --repo $ORYA_REPO"
```

Хуки спроектированы так, чтобы не ломать workflow при сбое: если `orya` недоступен, `opencode` продолжает работать, в логе появляется warning, но сессия не блокируется. Это важно для продуктивности — инструмент не должен становиться узким местом.

## 8. Формат `.orya/` — файлы и схемы

Папка `.orya/` живёт в корне каждого репозитория `Orya*` и коммитится вместе с кодом. Это гарантирует синхронизацию ментальной карты с состоянием репо на любом коммите.

```
.orya/
├── context.md              # автоматически генерируемый контекст для pre-session hook
├── manifest.yml            # мета-информация о репо и связях с другими репо Orya*
├── sessions/               # Provenance Tracker
│   ├── 2026-10-24-a1b2c3.yml
│   └── 2026-10-25-d4e5f6.yml
├── decisions/              # Decision Log
│   ├── d_2026-10-24-01.md
│   ├── d_2026-10-24-02.md
│   └── index.yml           # быстрый индекс для поиска
├── mental-model/           # Mental Model Reconstructor
│   ├── cards.yml           # SRS-карточки
│   └── graph.yml           # кросс-репо граф зависимостей
└── reviews/                # история orya review сессий
    └── 2026-10-24.log
```

**`manifest.yml`** — связующий файл между репо. Пример для `OryaAgent`:

```yaml
# .orya/manifest.yml в репозитории OryaAgent
repo: OryaAgent
role: orchestrator  # orchestrator | security | observability | ai | hs
description: |
  Оркестратор Orya-стека. Запускает агентов, маршрутизирует события,
  хранит conversation state.
depends_on:
  - repo: OryaSecurity
    interface: github.com/Reider85/OryaSecurity/pkg/policy.Evaluator
    used_in: internal/orchestrator/policy.go:42
    decision: d_2026-09-15-03  # почему именно этот интерфейс
  - repo: OryaObservability
    interface: github.com/Reider85/OryaObservability/pkg/tracer
    used_in: internal/orchestrator/tracing.go:18
  - repo: dieseldb  # внешняя зависимость
    interface: github.com/Reider85/dieseldb.Client
    used_in: internal/storage/diesel.go
exposes:
  - interface: AgentRunner
    package: github.com/Reider85/OryaAgent/pkg/runner
    consumers: [OriaAI, OriaHS]
principles:
  - "Оркестратор не содержит бизнес-логики, только маршрутизацию"
  - "Все долгоживущие состояния — в dieseldb, не в памяти"
  - "Каждая ошибка агента логируется в OryaObservability с trace_id"
```

**`context.md`** — генерируется командой `orya context` и перегенерируется автоматически при каждом коммите. Содержит выжимку для AI-агента: принципы, последние 10 decisions, активные слепые зоны, интерфейсы, которые репо экспортирует/потребляет. Длина — строго до 2000 токенов, чтобы помещаться в system prompt без переполнения контекста.

**`decisions/index.yml`** — индекс для быстрого поиска по тегам, файлам, репо. Без него `orya decisions --search` парсил бы все markdown-файлы при каждом вызове.

## 9. MCP-интерфейс

MCP-сервер `orya-mcp` выставляет инструменты и промпты, которые может вызывать любой MCP-совместимый клиент: `opencode`, Cursor, Claude Code, Cline. Это второй способ потребления (первый — CLI).

**MCP-tools:**

| Tool | Описание | Возвращает |
|------|----------|-----------|
| `orya.context` | Текущий контекст репо (то же, что `context.md`) | Markdown, ~2000 токенов |
| `orya.provenance` | История сессий, затронувших файл/строку | Список сессий с промптами |
| `orya.decisions` | Поиск decisions по тегам/файлам/репо | Список decision summary |
| `orya.mental_model` | SRS-карточки для текущего пользователя | JSON с due-карточками |
| `orya.first_person_explain` | Главное: объясняет файл от первого лица | Markdown-нарратив |

**`orya.first_person_explain`** — ключевой MCP-tool. Принимает путь к файлу и возвращает объяснение, написанное от вашего лица:

```
Tool: orya.first_person_explain
Input: { "file": "internal/middleware/ratelimit.go", "depth": "medium" }
Output (markdown):

## internal/middleware/ratelimit.go

Я добавил этот файл 24 октября, в сессии про rate limiting на
POST /v1/policies (session 2026-10-24-a1b2c3). На тот момент у
нас был открытый endpoint без ограничений, и любой валидный
токен мог заDoSить очередь обработки.

Я выбрал token bucket на 10 токенов с пополнением 1/6 сек.
Смотрел sliding window, но при 10 req/min накладные расходы
на хранение меток не оправданы — sliding window имеет смысл
при 100+ req/sec, у нас на три порядка меньше. Redis-based
вариант отверг, потому что multi-instance пока не нужен,
а точка отказа не нужна. Интерфейс Limiter абстрактен,
перенести в Redis можно без боли.

Что важно помнить: размер бакета вынесен в конфиг, можно
тюнить без релиза. Метрики экспортируются в OryaObservability
как ratelimit_deny_total — если она растёт, значит лимит
слишком агрессивный.
```

**MCP-prompts** (готовые шаблоны для типичных задач):

- `orya.pre_session_brief` — что показать агенту перед началом работы
- `orya.code_review_with_provenance` — ревью коммита с учётом исходного промпта и отвергнутых альтернатив
- `orya.archaeology` — раскопки конкретного файла: когда, почему, какие альтернативы

## 10. CLI — справочник команд

```bash
# === Инициализация ===
orya init                          # создать .orya/ в текущем репо
orya init --stack                  # инициализировать все 5 репо Orya* сразу

# === Provenance ===
orya who <file:line>               # кто и в какой сессии написал строку
orya when --pattern <regex> <path> # когда появился паттерн
orya why <file>                    # связать файл с decision log
orya sessions --since 7d           # список сессий за период
orya sessions --gaps               # коммиты без session trailer

# === Decision Log ===
orya decisions                     # все решения (по умолчанию за 30 дней)
orya decisions --today             # только сегодняшние
orya decisions --file <path>       # влияющие на файл
orya decisions --search <query>    # полнотекстовый поиск по текстам
orya decisions --gaps              # нетривиальные коммиты без decision
orya decisions new [--files ...]   # интерактивное создание записи

# === Mental Model ===
orya review                        # ежедневная SRS-сессия (~10 мин)
orya review --hard                 # только карточки с низким ease
orya review --blindspots           # файлы без SRS-карточек
orya review --regenerate --since 7d
orya review --stats                # статистика владения

# === Контекст и синхронизация ===
orya context                       # вывести context.md в stdout
orya context --refresh             # перегенерировать context.md
orya sync                          # обновить кросс-репо граф
orya tour <file>                   #guided-экскурсия по файлу

# === Hook-интерфейс (вызывается opencode) ===
orya hook pre-session --repo <name>
orya hook post-edit --repo <name> --session <id>
orya hook pre-commit --repo <name>

# === Отчёты ===
orya report --day                  # дневной отчёт: что сделано, что упущено
orya report --week                 # недельная ретроспектива
orya report --ownership            # heatmap владения по файлам
```

Все команды принимают `--repo <name>` для кросс-репо операций. По умолчанию репо определяется по текущему каталогу.

## 11. Дневной workflow

Инструмент встраивается в день без принуждения. Распределение по времени:

**Утро (10 минут).** Запуск `orya review`. SRS-сессия показывает 10-15 карточек с истекающим `due`. Большинство карточек — это файлы, которые вы не трогали 7/14/30 дней. Ответ на каждую занимает 10-30 секунд. Цель — поддерживать recall rate ≥75%. Если пропускать неделю, карточки копятся, и сессия превращается в марафон — это сигнал, что нужно пересмотреть принципы выбора файлов для SRS.

**Дневная работа.** Запускаете `opencode run "..."`. `pre-session` хук молча инжектирует `context.md` в system prompt агента. После каждой итерации `post-edit` хук обновляет `.orya/sessions/<id>.yml`. При нетривиальных изменениях (>50 строк) хук прерывает на 30 секунд для заполнения decision-черновика. Вы заполняете шаблон прямо в терминале, либо помечаете `trivial: true` и продолжаете.

Перед `git commit` срабатывает `pre-commit`. Если коммит нетривиален и не связан с decision — блокирует с подсказкой создать запись или пометить тривиальным. Сначала это раздражает, через 2 недели становится привычкой.

**Вечер (5 минут).** Запуск `orya decisions --gaps`. Показывает коммиты за день, у которых нет decision. Если такие есть — дозаполняете. Цель — coverage ≥90% для нетривиальных коммитов.

**Пятница (15 минут).** Запуск `orya report --week`. Возвращает: список всех decisions за неделю, heatmap владения по репо, recall rate за неделю, новые слепые зоны. Это точка ретроспективы: что из AI-сгенерированного за неделю вы реально понимаете, а что прошло мимо.

## 12. Метрики успеха

Инструмент считается работающим, если четыре метрики сходятся к целевым значениям за 8 недель использования.

**Authorship Confidence Score (ACS).** Микро-опрос: после каждого `orya review` сессии вы отвечаете на вопрос «Мог бы я написать этот код с нуля, если бы мне дали задачу?» от 1 до 5. Среднее за неделю — ACS. Цель: ≥3.5. Ниже 3.0 — сигнал, что MMR генерирует слишком простые карточки или что в проекте есть целые модули, которые вы не контролируете.

**Decision Coverage.** Доля нетривиальных коммитов (по `git log` за период) со связанной decision-записью. Цель: ≥90%. Это самая лёгкая метрика — её тащит `pre-commit` хук.

**Mental Model Reach.** Доля файлов в репо (взвешенная по LOC), которые покрыты хотя бы одной SRS-карточкой. Цель: ≥70%. Если ниже — нужно прогнать `orya review --regenerate --since 30d` для создания карточек из недавних decisions и изменений.

**Recall Rate.** Доля карточек в `orya review`, на которые вы ответили с оценкой ≥3. Цель: ≥75%. Если recall rate по конкретному репо (например, `OriaHS`) систематически ниже 60% — это сигнал, что вы не владеете этим репо, и нужно либо `orya tour` по слепым зонам, либо пересмотр архитектуры.

Метрики хранятся в `.orya/reviews/<date>.log` и агрегируются командой `orya report --metrics`.

## 13. Roadmap имплементации

Реализация разбита на три фазы. Каждая фаза самодостаточна: после неё инструмент уже полезен, можно останавливаться.

**Фаза MVP (1-2 недели).** Только Provenance Tracker и `context.md`.

- Команда `orya init` создаёт `.orya/` с базовой структурой
- `opencode` post-edit hook пишет `.orya/sessions/<id>.yml`
- `orya who` / `orya when` работают на основе session-логов
- `orya context --refresh` генерирует `context.md` из sessions
- pre-session hook инжектирует `context.md` в system prompt opencode

Результат: вы видите, какой промпт породил какой файл. Decision Log и Mental Model пока отсутствуют.

**Фаза v0.5 (3-4 недели).** Добавляется Decision Log и хуковая валидация.

- `orya decisions new` с TUI-шаблоном
- `pre-commit` хук блокирует нетривиальные коммиты без decision
- `orya why` связывает файл с decisions
- `decisions/index.yml` и полнотекстовый поиск
- Кросс-репо `manifest.yml` и команда `orya sync`

Результат: каждое решение зафиксировано с отвергнутыми альтернативами. Через год вы сможете объяснить, почему не Redis.

**Фаза v1.0 (6-8 недель).** Mental Model Reconstructor и MCP-сервер.

- `orya review` с алгоритмом SM-2
- Автоматическая генерация карточек типов 1-3
- Граф зависимостей `.orya/mental-model/graph.yml`
- `orya review --blindspots` и `--stats`
- MCP-сервер с 5 tools и 3 prompts
- `orya first_person_explain` через LLM (использует z-ai-web-dev-sdk или локальную модель)
- Метрики ACS / Coverage / Reach / Recall

Результат: полноценное ощущение авторства. Через 90 дней после начала использования recall rate стабилизируется ≥75%, и вы можете открыть любой файл любого репо `Orya*` и объяснить его так, как будто написали вчера.

## Что не входит в спецификацию 0.1

Сознательно вынесено за рамки текущей версии:

- **Web-дашборд.** CLI + MCP покрывают дневные задачи; визуализация графов отложена до v1.1.
- **Мульти-пользовательский режим.** Сейчас инструмент для одного автора; sync через git push/pull работает, но без слияния конфликтующих decisions.
- **Автоматическое написание decisions LLM-агентом.** Черновик создаётся из шаблона, но заполнение — за автором. Это сознательное трение: если решения пишет LLM, вы их не ассимилируете.
- **Поддержка не-Orya репо.** `dieseldb` и `strangecoin` учитываются как внешние зависимости, но не имеют собственного `.orya/`. Это можно изменить в v1.2.
